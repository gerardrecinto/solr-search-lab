What a build-log search index actually holds

The lab indexes synthetic CI build logs. This runs the repo's own log generator in your browser, so you can see the documents the Solr core receives. Search is not simulated here: it needs Solr. What you can see instead is the analysis chain and the measured query costs, taken from the README.

Copied from the README, which says it was checked against Solr's /analysis/field endpoint. Synonyms expand at index time, so a search for oom is a plain term match.

Deep paging costs more with start=N

Measured by the repo on 8,000 synthetic lines, one local node, from the README. Not re-run here.

Query time by offset

start=N makes Solr walk and discard the first N matches on every request. cursorMark resumes from the last sort value, so it does not slow with depth. The trade-off is that it only walks forward and cannot jump to page 47.

Plain vs faceted query

Faceting added a few milliseconds on this dataset. The lab has no multi-node or production-scale measurement.

Three real incidents

1. Synonym updates need a core reload

A synonym added through the Managed Resource API changed the on-disk map but not the running analyzer. Analyzing OutOfMemoryError showed no oom token until a core RELOAD ran. Setup now always reloads.

2. Dynamic core creation needs a registered configset

The first create_core() failed because the default configset was not in the shared path.

Could not load configuration from directory
/var/solr/data/configsets/_default

Fix: a one-time, idempotent copy from the running core.

3. pysolr auto-paginates on iteration

Looping over a pysolr results object while also running a manual cursorMark loop returned 539 documents from a 137-document test. Reading the single page of docs fixed it, and a regression test now covers it.

Run it yourself

Docker and Python 3.12.

docker compose up -d
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install -e .
python -m solr_search_lab.config.setup_schema
python -m pytest tests/ -v
python scripts/query_performance.py
What this does not do
  • It is a standalone single-node Solr lab, not SolrCloud.
  • The data is synthetic. The timings come from one local machine and prove nothing about production load.
  • Changing the synonym list only affects documents indexed afterwards. Older documents need a reindex, which the lab covers with a core swap.
  • This page cannot run queries, because it has no Solr behind it.
